# Phase 8.10: Architecture Profile Evaluation And Documentation

## 0. Execution Gate

| Field | Value |
|---|---|
| Issue | [#148 Produce Phase 8 evaluation evidence and final documentation](https://github.com/TVJunkie724/master-thesis/issues/148) |
| Branch | `codex/phase-8-evaluation-documentation` |
| Required base | Reviewed zero-finding `six-layer-eventing@1` commit, which itself pins the reviewed Five-layer v2 digest |
| Mode | Offline deterministic regeneration; no provider credentials or live resources |
| LaTeX | Excluded without separate explicit authorization |

This plan evaluates the committed implementations. It cannot redesign a
profile, substitute a service, repair an incomplete cost formula, or turn a
failed candidate into a total. Such a finding reopens the owning implementation
issue before evaluation resumes.

## 1. Research Outcome

Produce one immutable evaluation package that lets a reviewer reproduce and
inspect:

1. the inherited/paper-compatible `five-layer-baseline@1` as historical
   reconstruction evidence;
2. `five-layer-baseline@2` with the complete service bundles and mandatory
   embedded event behavior;
3. `six-layer-eventing@1` with identical domain behavior and the independent
   Event Layer delta.

Functional completeness and differences are reported before cost. The result
does not claim that unlike provider services are equivalent, that estimated
cost equals an invoice, or that one profile is a universal optimum.

## 2. Frozen Evaluation Inputs

The evaluation manifest must pin:

- architecture, provider, component, permission, package, Terraform,
  bootstrap, access, workload, scenario, pricing, formula, and source digests;
- RDS/Manifest versions and each resolved architecture digest;
- AWS `eu-central-1`, Azure `westeurope`, and GCP `europe-west1`;
- one declared currency conversion/evidence observation timestamp policy;
- core Small/Medium/Large v2 presets and the separately versioned event
  Small/Medium/Large scenarios paired by size;
- solver/config version, repository commit, container image digests, command,
  platform, and generated result digests;
- supported, unsupported, unverified, and historical statuses.

No input is inferred from chat history or a mutable provider console.

## 3. Experiment Matrix

### 3.1 Five-layer v2

For each Small/Medium/Large workload, evaluate:

- three single-cloud placements;
- all six `provider(L3_hot/L5) != provider(L4)` placements;
- the registered mixed L1/L2/cool/archive assignments generated by the profile
  solver, with unsupported results preserved by reason code;
- local and remote Twin projection;
- local and remote storage transitions;
- no Event Layer component, but the exact embedded-event/direct/bridge behavior
  required by the profile.

### 3.2 Six-layer v1

For each paired Small/Medium/Large workload, evaluate:

- three provider-local Event Layer placements;
- all six directed cross-cloud event bridge pairs;
- representative valid three-provider hub/spoke compositions from the
  registered graph rather than an assumed fixed hub;
- the same inherited L1-L5 placement matrix and workload as Five-layer v2;
- exact Event Layer incremental services, capacity, transfer, observability,
  failure, and bridge cost.

### 3.3 Historical v1

Reproduce only the committed historical scenarios supported by
`five-layer-baseline@1`. Do not add GCP support, events, workload-v2 fields, or
new cost dimensions retroactively. Clearly separate historical reconstruction
from the functionally aligned v2 comparison.

source header and must be byte-identical for identical frozen inputs.

## 5. Interpretation Rules

- Report functionality/capacity status before cost totals.
- Never publish a total for an incomplete, unsupported, stale, or unverified
  candidate.
- Compare Five-layer v2 and Six-layer v1 only for identical paired workload,
  region, price/evidence, and inherited L1-L5 assignment context.
- Separate total cost from the Event Layer incremental delta.
- Attribute fixed shared resources once and disclose the allocation rule.
- Separate service, request/throughput, storage, transfer, tiering,
  observability, failure/replay, visualization-seat, and bridge categories.
- Show same-provider zero bridge/egress where the contract says none.
- Do not interpret provider price differences as service equivalence or
  production fitness.
- Label theoretical capacity and offline Terraform validation separately from
  measured live throughput and successful live access; the latter remain
  pending until a separately approved supervised run.

## 6. Research Question Mapping

| Question | Required evidence |
|---|---|
| RQ1 | Function-and-edge reconstruction, profile contracts, provider/component mappings, and architecture deltas |
| RQ2 | Functional completeness, capacity gates, resolved paths, deterministic Deployer/Terraform realization, and unsupported reasons |
| RQ3 | Profile-separated cost results for frozen scenarios and placements |
| RQ3.1 | Single-cloud versus multicloud transfer/tiering/bridge/component decomposition |
| RQ3.2 | Five-layer v2 embedded-event behavior versus Six-layer independent Event Layer functionality and incremental cost |

The exact research-question wording remains owned by the cited research design;
this plan maps evidence and does not edit thesis prose.

## 7. Current-System Documentation

After evidence generation, update implemented behavior only in:

- root README, onboarding, Phase 8 README/HANDOFF, and contract maps;
- Optimizer, Management, Deployer, Terraform/provider, permission/bootstrap,
  and troubleshooting docs-site pages;
- Flutter README, `FRONTEND_ARCHITECTURE.md`, Configuration Workspace and
  Frontend Delta roadmaps/phases, implementation references, and setup/runbook;
- `docs/research/README.md` plus research reasoning, evaluation method,
  limitations, and evidence index.

Documentation must explain the exact manual user lifecycle:

1. create/obtain provider bootstrap authority outside the app;
2. enter it into guided setup;
3. retain the generated bounded CloudConnection and truthfully complete any
   manual revocation;
4. create/configure/calculate/select the Twin without further admin authority;
5. resolve deployment-preflight provider prerequisites;
6. deploy only in a separately approved supervised run;
7. open the generated L4/L5 surfaces when live access has been verified.

Do not publish a browser password, cloud identifier, generated credential,
Terraform state, raw provider response, or example that resembles a secret.

## 8. Reproducibility And Verification

Mandatory safe gates:

```bash

./thesis.sh test frontend
THESIS_DOCKER_CONTEXT=orbstack ./thesis.sh test frontend-integration
docker --context orbstack compose --profile docs run --rm docs mkdocs build --strict
```

The evaluation generator must also pass:

- schema/reference/digest and mutation tests;
- two clean consecutive regenerations with byte-identical JSON/Markdown;
- scenario cardinality and pair-coverage assertions;
- cost recomputation and exact-once ownership assertions;
- functional-before-cost and no-total-for-rejection assertions;
- source URL/digest/date/license metadata checks;
- secret/provider-identifier/absolute-path/nondeterministic timestamp scans;
- clean-worktree generation check.

Tests may use only frozen local evidence and credential-free Docker services.
No pricing refresh requiring provider authority, Terraform apply/destroy,
browser sign-in, load generation, or live provider API is part of this phase.
